# Squad UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the squad tab from a stub into the full path from "no squad" to "looking at a ranked leaderboard" — create, join by 6-digit code, and the board itself.

**Architecture:** All three squad RPCs already exist and are tested (`create_squad`, `join_squad`, `squad_leaderboard`). This is app work: TanStack Query hooks over those RPCs, a small set of presentational components, and one screen that orchestrates them. Pure rules (invite-code normalisation) live in their own zero-import module so root Vitest can load them.

**Tech Stack:** Expo SDK 57 · Expo Router (typed routes) · React Native 0.86 · TanStack Query · Zustand · `@kairo/core`

## Read this first — context a fresh session does not have

**Start by reading `CLAUDE.md` in the repo root.** It documents the architecture, the environment constraints, and the invariants. Everything below assumes it.

### What already exists server-side — do NOT rebuild it

Three `SECURITY DEFINER` RPCs, all live on project `zniopywbwenrzxezolwv` and covered by the PGlite suite:

```
create_squad(p_name text) returns public.squads
join_squad(p_invite_code text) returns public.squads
squad_leaderboard(p_squad_id uuid, p_local_date date default null, p_mode text default 'current')
```

`squad_leaderboard` returns these columns, in this order:

```
rank bigint, user_id uuid, character_name text, class text, level integer,
local_date date, total integer, tiers jsonb, contributing_stats smallint,
has_rec boolean, flagged boolean, status day_status, current_streak integer,
is_self boolean
```

`p_mode` is `'current'` (each member's day in progress) or `'completed'` (each member's own yesterday). An unrecognised value raises. **In `'completed'` mode, members in different timezones legitimately return different `local_date` values in one result set** — that is the mode working, not a bug.

`squad_leaderboard` is the privacy projection (§5): squadmates see tiers and scores, never raw steps or hourly movement. **Do not add a query that reads another user's `health_buckets` or `profiles` row — those are owner-only by RLS, and widening them defeats a structural guarantee.**

### RLS facts that shape the client

- `squads` has `squads_select_member` — a plain `select * from squads` returns only squads the caller belongs to. That *is* the "my squad" query; no filter needed.
- `squad_members` has `INSERT` and `UPDATE` revoked from `authenticated`. Joining is only possible through `join_squad`. There IS a `squad_members_delete_self` policy, so leaving a squad is client-possible — but **leaving is out of scope for this plan**.
- Free squads cap at 6 members, Legendary at 15. A per-user squad cap is enforced by trigger.

### There is already a squad with data in it

The live project holds a seeded squad: your own account plus five fake members (`Rival1`–`Rival5`), with a week of activity across three personas. Approximate daily totals: sedentary ≈ 1,100, average ≈ 3,850–4,050, athlete ≈ 4,850.

**This is what Task 5 verifies against.** You do not need to seed anything. If you do want more data, `seed-health` is deployed and its secret is at `supabase/.temp/seed-secret.txt` (gitignored) — but treat that as a last resort, not a routine step.

### Environment constraints

Port 5432 is blocked, Supabase's direct host is IPv6-only here, and Docker is unavailable. `supabase db push`, `psql` and `supabase start` all fail, and none of that indicates a broken project. What works, all HTTPS:

- SQL against the live project: `./supabase/scripts/remote-sql.sh "<sql>"`
- Schema tests: `npm run test:schema` (PGlite, no Docker)
- Function deploys: `supabase functions deploy`

**This plan adds no migrations**, so none of that should be needed beyond read-only verification in Task 5.

## Design decisions already made — do not relitigate

| Decision | Choice | Why |
|---|---|---|
| Default view | **Live board (`'current'`)** | §2's hooks assume a board you check during the day ("1 hour left. You're in Nth place"). Completed-day is a secondary toggle. |
| `current_streak` in completed mode | **Hide it** | The RPC returns *today's* streak regardless of the ranked date, so in completed mode the number and the day disagree. Showing streaks only on the live board removes the mismatch at zero cost. Fixing it in SQL was considered and deferred. |
| Realtime | **Out of scope** | The trigger and RLS policy exist server-side; wiring the subscription is its own follow-up. PGlite cannot verify Realtime, so it needs live testing. |
| Row design | **Reuse `StatBar` and the existing theme tokens** | The squad and character screens should read as one app. Task 1 fixes `StatBar`'s ceiling bug first rather than duplicating it. |
| Leaving a squad | **Out of scope** | The RLS policy exists; the UI is a separate decision (leader succession, confirmation). |

## Task 1: Fix the featured-stat ceiling before reusing StatBar

`StatBar` sizes its fill against `STAT_MAX = 900`, the Gold tier ceiling. But §6's weekly specialization multiplies one stat by 1.5, so a **featured Gold stat scores 1,350** — it pins the bar at 100% and looks identical to a non-featured Gold. /**
 * Invite-code rules, mirroring the database CHECK `^[A-Z0-9]{6}$`.
 *
 * Codes get read aloud in group chats and retyped, so normalisation is
 * deliberately forgiving: case, surrounding space, and the dashes people add
 * to break up six characters are all stripped before validating. What reaches
 * `join_squad` is always the canonical form.
 *
 * Zero imports so root Vitest can load this — it has no `@/` alias and cannot
 * parse React Native's Flow syntax.
 */

export const INVITE_CODE_LENGTH = 6;

export function normalizeInviteCode(raw: string): string {
  return raw.replace(/[\s-]/g, '').toUpperCase();
}

export function isValidInviteCode(raw: string): boolean {
  const code = normalizeInviteCode(raw);
  return new RegExp(`^[A-Z0-9]{${INVITE_CODE_LENGTH}}$`).test(code);
}
```

import { useQuery } from '@tanstack/react-query';
import { supabase } from '@/lib/supabase.ts';

export type Squad = {
  id: string;
  name: string;
  invite_code: string;
  leader_id: string;
  max_members: number;
};

export type LeaderboardMode = 'current' | 'completed';

/** Exactly the columns squad_leaderboard() returns. */
export type LeaderboardRow = {
  rank: number;
  user_id: string;
  character_name: string;
  class: string;
  level: number;
  local_date: string;
  total: number;
  tiers: Record<string, string>;
  contributing_stats: number;
  has_rec: boolean;
  flagged: boolean;
  status: 'provisional' | 'final';
  current_streak: number;
  is_self: boolean;
};

export const squadKeys = {
  mine: (userId: string | undefined) => ['squad', 'mine', userId ?? 'none'] as const,
  board: (squadId: string | undefined, mode: LeaderboardMode) =>
    ['squad', 'board', squadId ?? 'none', mode] as const,
};

/**
 * The caller's squad, or null.
 *
 * `squads` is filtered by the `squads_select_member` policy, so an unqualified
 * select already returns only squads the caller belongs to — the RLS policy is
 * the filter, and adding a client-side one would just duplicate it.
 *
 * MVP allows one squad per user (enforced by trigger), so `maybeSingle()` is
 * correct; null means "not in a squad", which is a normal state, not an error.
 */
export function useMySquad(userId: string | undefined) {
  return useQuery({
    queryKey: squadKeys.mine(userId),
    enabled: Boolean(userId),
    queryFn: async (): Promise<Squad | null> => {
      const { data, error } = await supabase
        .from('squads')
        .select('id, name, invite_code, leader_id, max_members')
        .maybeSingle();
      if (error) throw new Error(error.message);
      return (data as Squad | null) ?? null;
    },
  });
}

export function useSquadLeaderboard(
  squadId: string | undefined,
  mode: LeaderboardMode,
) {
  return useQuery({
    queryKey: squadKeys.board(squadId, mode),
    enabled: Boolean(squadId),
    queryFn: async (): Promise<LeaderboardRow[]> => {
      const { data, error } = await supabase.rpc('squad_leaderboard', {
        p_squad_id: squadId as string,
        p_local_date: null,
        p_mode: mode,
      });
      if (error) throw new Error(error.message);
      return (data ?? []) as LeaderboardRow[];
    },
  });
}
```

- [ ] **Step 6: Write the mutations**

Create `src/features/squad/mutations.ts`:

```ts
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { supabase } from '@/lib/supabase.ts';
import { normalizeInviteCode } from './invite-code.ts';
import { squadKeys, type Squad } from './queries.ts';

/**
 * Turns a Postgres error into something a person can act on.
 *
 * The RPCs raise with specific SQLSTATEs, and rendering their raw text would
 * put `new row violates row-level security policy` in front of someone who
 * just wanted to join their friends.
 */
function squadErrorMessage(code: string | undefined, fallback: string): string {
  switch (code) {
    case '22023':
      return 'That code does not match any squad. Check the six characters and try again.';
    case '42501':
      return 'Finish setting up your character first.';
    case '23514':
      return 'That squad is full.';
    default:
      return fallback;
  }
}

export function useCreateSquad(userId: string | undefined) {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (name: string): Promise<Squad> => {
      const { data, error } = await supabase.rpc('create_squad', {
        p_name: name.trim(),
      });
      if (error) {
        throw new Error(
          squadErrorMessage(error.code, 'Could not create the squad. Try again.'),
        );
      }
      return data as Squad;
    },
    onSuccess: () =>
      queryClient.invalidateQueries({ queryKey: squadKeys.mine(userId) }),
  });
}

export function useJoinSquad(userId: string | undefined) {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (rawCode: string): Promise<Squad> => {
      // join_squad is idempotent — tapping an invite twice is a normal thing
      // to do and must not read as an error.
      const { data, error } = await supabase.rpc('join_squad', {
        p_invite_code: normalizeInviteCode(rawCode),
      });
      if (error) {
        throw new Error(
          squadErrorMessage(error.code, 'Could not join that squad. Try again.'),
        );
      }
      return data as Squad;
    },
    onSuccess: () =>
      queryClient.invalidateQueries({ queryKey: squadKeys.mine(userId) }),
  });
}
```

- **`current_streak` is rendered only when `mode === 'current'`.** In completed mode the RPC returns today's streak beside yesterday's score, and showing them together is a mismatch with no explanation. This is a deliberate decision, not an oversight — leave a brief comment saying so.

- `row.status === 'provisional'` in completed mode means the day has not finalized yet. Indicate it subtly rather than hiding the row.

## Notes for whoever executes this

**Things that will look wrong and are not:**

- In `'completed'` mode, members in different timezones return **different `local_date` values in one result set**. That is the mode working — every player's day runs midnight-to-midnight in their own zone (§2).
- Your own row may show a total of 0. The seeded members have activity; your account has none, because nothing reads HealthKit yet (that is Phase 3).
- `squad_leaderboard` raises `authentication required` when called through `remote-sql.sh`. That script runs as the table owner, where `auth.uid()` is null. Verify the RPC from the app, not the shell.

**Do not:**

- Add npm dependencies, or install `react-native-svg`.
- Query another user's `profiles` or `health_buckets` row. Everything about a squadmate comes through `squad_leaderboard`, which is a privacy projection with no argument that returns raw steps.
- Put an `@/` import or a React Native import into `invite-code.ts`. Root Vitest cannot load either, and the test file beside it would stop running.
- Write a migration. This plan needs none.
